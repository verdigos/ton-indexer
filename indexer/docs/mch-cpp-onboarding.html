01Mission in 30 seconds

The TON event classifier turns blockchain traces into structured Action rows. Historically each of ~30 protocols was a hand-written Python BlockMatcher. Production needs that classifier in C++, and keeping two hand-written codebases in sync forever was the non-starter. So the matchers moved into a declarative DSL — MCH (.mch files) — which a Python frontend compiles into a language-neutral IR artifact (JSON). Any runtime that implements the IR semantics classifies identically.

ton-mch-engine is the C++ runtime of that IR. It loads the artifact, walks the block tree matching patterns, runs the build programs, and produces classified blocks — with zero Python in the build. Its north star is byte-identical output against the Python IR engine, which is the semantics oracle.

What it is

A td-actor C++ program plus a build-time codegen tool. Reads .lz4 trace fixtures (today) / live traces (future), an IR JSON artifact, and emits classified Blocks. Every layer was accepted only after a byte-identical A/B against the Python reference over the 147-fixture corpus.

What it is NOT

Not a compiler — it never reads .mch source. Not a general interpreter — expressions and build programs are codegen'd to straight-line C++. No hot reload, no cross-trace state, no coroutines. A trace is processed in isolation, always.

✓ The mental model that unlocks everything

Two runtimes implement one IR. Python is ground truth (reference + debugging). C++ is production-bound (fast, Python-free). The IR JSON is the version-controlled contract between them, committed under ir/. Nothing in C++ "decides" semantics — it either matches Python or it's a bug.

05The Value type

Value (Value.h) is the C++ mirror of the Python reference values the expression evaluators produce and consume. It is a tagged variant — a VType enum plus a flat set of payload members — designed to stay cheaply copyable (containers behind shared_ptr; values are immutable once built).

enum class VType {
  Null, Bool, Int, Str, Bytes,
  Amount,   // td::RefInt256 nanoton-style amount; null num == Python Amount(None)
  Account,  // AccountId (raw addr or addr_none)
  Asset,    // TON | jetton-master
  Cell, List,
  Dict,     // pure key lookup
  Obj,      // attribute access + .exit_code
  Block,    // reference to a matched Block
};
Why RefInt256, not int64

Every expression integer (Int and Amount) is td::RefInt256. Python ints are unbounded and jetton amounts overflow int64 — a fixed 256-bit big-int is the faithful carrier. int64 inputs (JSON numbers, host fields) widen on entry. This is why rt_add et al. compare via cmp(*ln,*rn) on RefInt256, never native +.

addr_none is a state, not null

Account carries a distinct addr_none flag — a present-but-empty address, mirroring Python AccountId(None): repr is "addr_none", as_str() is null. It is not the same as a null Value. Address equality special-cases it: addr_none == addr_none only.

Dict vs Obj — two map kinds

Both hold vector<pair<string,Value>>, but differ in attribute-access semantics. Dict is pure key lookup (Python dict / block data map / record literal). Obj is attribute access with the special .exit_code envelope accessor (Python SimpleNamespace — the decode of a message envelope / body / lookup record).

Block as a value

VType::Block holds a non-owning const Block* (the arena outlives all values). It exposes the msg/data/failed/broken/btype accessors, and — matching Python's Block.__eq__ — compares by identity. This is what lets a build's consumed be a List of Block values.

Asset == string is a case-insensitive compare of the jetton master's raw string (Python Asset.__eq__ lowercases both sides); the TON asset matches the literal "ton". These are the kinds of tiny fidelity rules that live in ExprRuntime.cpp and matter for byte parity.

06The one-semantics rule

This is the single most important invariant in the module. All leaf semantics live in ExprRuntime.{h,cpp} as rt_* free functions. Two consumers call them — the tree-walking interpreter and the generated straight-line C++ — so a codegen bug can never be masked by a subtly different runtime. If codegen output disagrees with the interpreter, codegen is wrong (or you found an interpreter bug — stop and report, do not silently fix).

Here is the same rt_add call reached from both paths. Watch the shape: if (r.faulted) return …; threading is identical because both call one function.

Interpreter — ExprEval.cpp (eval_binary)
// after evaluating l and r operands…
if (op == "==") return rt_eq(l.value, r.value);
if (op == "!=") return rt_ne(l.value, r.value);
if (op == "<")  return rt_lt(l.value, r.value);
if (op == "+")  return rt_add(l.value, r.value);
if (op == "-")  return rt_sub(l.value, r.value);
if (op == "*")  return rt_mul(l.value, r.value);
Generated — builds_generated.cpp (build_0)
// ...value + 5, emitted straight-line
Value v15 = std::move(r15.value);
static const td::RefInt256 lit16 =
    td::dec_string_to_int256(std::string("5"));
Value v16 = Value::make_int(lit16);
EvalResult r17 = rt_add(v15, v16);
if (r17.faulted)
    return BuildOutcome::rejected(std::move(r17.message));
Value v17 = std::move(r17.value);
✓ The fault model that makes this work

A fault is a distinct outcome, never a thrown exception. Every op returns EvalResult{faulted, value, message}. The generated code threads them with straight-line early returns; the interpreter does the same recursively. Null propagation is baked into each rt_* exactly as Python does it (arith null→null, ordering null→false, == structural, builtins null-strict) — so call sites never special-case null except the lazy operators (and/or/??/ternary), which are control flow and stay at the call site (see ExprEval::eval_binary).

07Walker semantics you must not break

The walker (Walker.cpp, class MatchState) is a literal port of the Python reference walker. Matching never mutates the tree — every matcher runs over the same shared block tree, which is what makes the match phase cleanly A/B-able. Here are the edge semantics that are easy to get subtly wrong; each is legacy parity, not a design choice you can "improve".

Child edge = multi-match, NOT first-win

The child matcher is tried on every next_block and all full matches accumulate. Two matching children → both consumed. A scalar capture takes the first binding.

for (Block *cand : canonical(block->next_blocks)) {
  Mark mk = mark();
  if (match_node(node.child, cand)) matched_any = true;
  else rollback(mk);
}
return matched_any || nodes[node.child].optional;

Children set = ordered, first-match-wins

Over a working copy of next_blocks: each declared item scans the working set in order, takes the first candidate that matches its full subtree, and removes it from the working set. A required item that finds nothing fails the node.

for (int item : node.children) {
  for (i in working) {
    if (match_node(item, working[i])) { working.erase(i); break; }
    rollback(mk);
  }
  if (!matched && !nodes[item].optional) return false;
}
Mark / rollback — the savepoint discipline

Every speculative sub-attempt is bracketed by mark() / rollback(mk). A Mark is three sizes: bindings, consumed, frames. Rollback truncates all three and erases the un-consumed blocks from the visited_ set. A failed sub-attempt therefore leaves zero residue — this is what makes clean rejection (§10.7) possible.

Recursion — frontier vs cyclic

Frontier (default): step nodes advance a frontier of the previous step's consumed-blocks' children; exit is attempted first per candidate; success iff ≥1 step landed. Cyclic (tonco-style back-edges): plain descent into node.step. List captures get gap-aligned nullptrs per iteration so parallel lists stay index-aligned (spec §7.2) — see assemble_captures.

⚠ Canonical order: substrate maintains, walker reads raw

The Python engine sorts candidates (_canonical, min_lt asc) at every walk site. The C++ substrate keeps next_blocks canonical as an invariant, so canonical() in the walker is a no-op for a single block's next_blocks and only reorders the recursion frontier's concatenation — matching Python. Don't "optimize away" the canonical() calls; they are load-bearing exactly at the frontier.

✕ Clean rejection (spec §10.7)

In try_build: a reject when firing, any expression fault, or a merge_blocks returning false ⇒ clean rejection. Nothing is consumed, no side effects, no excess/bounce auto-append, and the anchor stays available to later matchers. In the walker's contract: None = structural mismatch, [] = clean rejection, non-empty list = [produced, *auto_appended]. A produced block is invisible to the pass that made it but visible to later matchers — which is how ethena_deposit anchors on a jetton_transfer block the jettons matcher produced moments earlier. Corollary: matcher order matters for composed anchors (see hazards).

08Two-phase lookups (D1)

Build programs are pure except lookup — interface-repository reads (jetton wallets, NFT items, nominator pools). Rather than coroutines, the C++ side runs the generated build fn twice against different lookup tables. Deterministic, testable offline, and it batches naturally per trace (one actor-request round in production).

A single dry pass can't see a lookup whose argument is another lookup (the inner null short-circuits the outer before its key forms). So collect re-runs until no new misses appear.

Three LookupTable implementations back the cycle, all in BuildRuntime.h:

  • CollectingLookupTable — has() covers exactly the artifact's kind set (registration-first fault order); get() serves already-fetched values and records misses.
  • FilledLookupTable — immutable fetched values; missing key → null (nullable-lookup semantics).
  • FixtureLookupSource — the offline LookupSource over a fixture's interfaces section, mirroring the real registered Python lookup fns (jetton_wallet uppercases its key, nft_item uses the raw key, nominator_pool…). Production swaps this for an actor-request adapter (Phase G).

Fault ordering is copied statement-for-statement: rt_lookup_build faults on an unregistered kind first, then applies null-strict argument handling (any null arg → null, table untouched), then reads the table — exactly as Python's expr.py _eval_lookup.

09The codegen story

Two reasons expressions and build programs are codegen'd rather than interpreted in C++: (1) no hot reload means the artifact is known at build time; (2) generated straight-line C++ beats a tree-walker. The generator is itself a C++ tool — mch-codegen — so the C++ build has zero Python dependency.

    DEPENDS tlbc ${...}/tlb/mch-msgs.tlb ...)

The sha256 identity guard — and the incident that forced it

mch-codegen hashes the input document's bytes (before json_decode mutates the buffer) and bakes the hex into the generated table as gen_builds_source_sha() / gen_wheres_source_sha(). At load, the runner compares it against the artifact's source_sha256 and hard-fails (exit 2) on mismatch:

if (ir.source_sha256 != gen_builds_source_sha()) {
  fprintf(stderr, "generated build table was built from a DIFFERENT artifact "
          "(table sha %s, loaded %s) — regenerate: mch-codegen --builds ...", ...);
  return 2;
}
⬢ War story · the stale-pairing incident

This guard exists because a stale table paired with a fresh artifact once produced a convincing-but-wrong A/B failure — the diff looked like a real semantic bug but was just a mismatched generated file. Debugging a phantom is expensive; the sha guard turns that whole class of confusion into an immediate, unambiguous exit-2. When you see the "DIFFERENT artifact" message: you edited the IR and forgot to regenerate. Run the printed command.

Byte-determinism of codegen is itself a gate: delete vectors_generated.cpp, rebuild, and it must regenerate byte-identical.

09bThe BOC byte-parity war story

⬢ War story · pytoniq cell order ≠ td cell order

Cell-derived strings land in DB-visible data (vesting's message_boc_str, jetton forward_payload). The naive expectation — "standard BOC serialization matches across languages" — was FALSE.

pytoniq's Cell.order() is a pre-order DFS where a revisited cell is popped and re-appended with its subtree re-walked — so shared cells sink to their last visit. td's std_boc_serialize orders cells differently. For any multi-ref tree the two produce byte-unequal output, even though the root hash is equal.

Rather than bless a permanent cross-language byte divergence in DB rows, C++ carries pytoniq_to_boc() (~100 LOC in Value.cpp) that emulates pytoniq's writer container layout exactly.

The subtlety that bites: CRC is set per call site, because the Python code paths differ. Jetton payload bytes come from an explicit to_boc(hash_crc32=True); a bare b64(Cell) uses to_boc() defaults (crc off). So the C++ side mirrors each:

// MsgParse.cpp — jetton payload bytes: crc ON (jettons.py explicit hash_crc32=True)
td::Result<std::string> boc_bytes(const td::Ref<vm::Cell> &c) {
  return pytoniq_to_boc(c, /*hash_crc32=*/true);
}
// b64(Cell) builtin: crc OFF (bare to_boc() defaults) — different call site
◆ Note the design-doc tension (report, don't fix)

mch-cpp-buildprog-design.md §D4 records the user's pre-implementation assessment that raw-byte equality via std_boc_serialize(cell, 0) should suffice and that the "different ref layouts" finding was "suspected self-inflicted". The committed code (and mch-overview.md §4, plan §10) reflects the opposite conclusion after task B0: the divergence was real, and pytoniq_to_boc is the shipped answer. When reading D4, treat it as historical; the code is ground truth.

The Python-twin concept

Each C++ dump mode has a Python twin script (lives in the session scratchpad, not committed) that drives the real Python engine internals and prints the same canonical dump format. diff must be 0. Dump keys avoid anything unverified cross-language: a block key is btype#opcode@min_lt — never a raw tx-hash string (unless the string form itself was A/B'd).

The skip-table honesty rule

A matcher missing a host binding is skipped — but by the same rule from the same artifact data on both sides. So the skip set itself is A/B'd and nothing drops out silently. Skip tables must always be computed from the artifact, never from registry availability — that's what keeps twins honest. In C++ this is build_skip_reason() in Classify.cpp emitting SKIP <name> reason=… lines.

Conformance vectors are the other half: expr_vectors.json (91: every expr kind, builtin, operator, null-propagation, fault) and build_vectors.json (25: every statement kind, rejection, lookup). Expectations are generated by running the real Python evaluators — never hand-authored. The generated-vs-interpreter split (§06) means each vector is checked on both C++ paths too.

11Build workflow

Windows (dev) — the critical path
  • Build only via the scratchpad wrapper bat: it calls vcvars64.bat then CLion's cmake --build … --target ton-mch-engine (add --target mch-codegen when iterating on the tool).
  • Never run cmake configure under vcvars — libpqxx try_compile breaks. Configure happens in a plain environment (the IDE does it on CMakeLists change).
  • After editing a CMakeLists, the first bat run may fail with a transient libpqxx "Permission denied" recompaction error — just re-run the bat once.
  • MSVC gotchas: td::Slice ctor is explicit (wrap const char*); #include <iostream> for std::cout; WIN32_LEAN_AND_MEAN is repo-wide — don't remove.
Linux (production) — normal expectations
  • Standard CMake through the vcpkg toolchain; the engine target builds like any other ton-index-worker binary.
  • The C++ build is Python-free: mch-codegen + tlbc run as build-time custom_commands; the committed generated files mean a clean checkout builds without a codegen step first.
  • Production lookups become an actor-request LookupSource (Phase G); the artifact is embedded at build or loaded once at startup — no hot reload machinery anywhere.
⚠ td::json_decode mutates its buffer

JsonValue holds Slices into the buffer you decoded — keep buffers alive. The WhereExpr self-owned-buffer pattern (a std::string buf the decoded expr points into, both behind one shared_ptr) is the template to copy when you need a JSON subtree to outlive its parent document.

◆ How a new parser family grows coverage

Add constructors to tlb/mch-msgs.tlb → tlbc regenerates parsers → wrap them in a MsgParse adapter reproducing the pytoniq quirks → verify with --parse-dump A/B (families absent from the corpus get synthetic body tests: build the BOC in the twin with pytoniq, feed both sides). Each family a declarative matcher's parse statement needs flips that matcher out of the skip table and into the classify A/B — that's the coverage lever. Host predicates/fns (Phase D) do the same for the pred-skipped matchers, registered in a HostRegistry the loader checks instead of marking unrunnable.

13Standing hazards (memorize)

✕ Frontier diamond-dup deviation

find_frontier dedups where Python's find_next keeps duplicates on diamond shapes. This is suspect #1 on any future diamond-trace A/B diff.

✕ Matcher ordering ties break on FILE NAME (T20)

All specs default to priority 100, so ties break on file name. The production artifact orders ethena_deposit before jetton_transfer (e<j), so a composed-btype matcher can never see blocks produced by a later-named matcher within one engine pass. B3 classify worked around it by prefixing the decl-jettons file a_. Production wiring (T26) must review spec priorities.

⚠ Leaf .data in C++ is a SUBSET

extra_currencies / ton_transfer comment are omitted — reading them faults where Python yields a value. Wire them through MsgParse when a spec first needs one. Same for envelope .msg fields the loader doesn't decode (fwd_fee etc.) — extend TraceLoader on first use.

⚠ Outer classify BFS visits siblings in canonical (min_lt) order

Consistent with the substrate invariant on both A/B sides, but not byte-order-identical to production Python event_processing (raw insertion order). Matters only when overlapping matches race on sibling order; revisit at Phase G production parity.

⚠ The gitignore trap

Python .gitignore's [Bb][Uu][Ii][Ll][Dd]* hides indexer/events/mch/builders/ — the host-binding source you'll cross-reference. Use git add -f. (C++-side generated files are committed normally.)

14Glossary

btypeA block's type string (ton_transfer, call_contract, jetton_transfer, a produced action btype…). Compared as a raw std::string — interning was deferred as a pure perf win with no observable effect.
anchorThe single distinctive block that triggers a match attempt — an opcode, opcode set, btype, or (host) predicate. matcher_test_self gates on it.
capture slotCapture names exist only at compile time; the walker binds slot numbers (D3). WhereEnv/BuildEnv carry a const Value *slots. Keeps generated code free of string maps.
artifactThe compiled IR JSON (ir/mch_ir.json). The version-controlled cross-language contract; consumed by both runtimes, hashed for the sha guard.
consumed setThe blocks a match claimed, in traversal order, identity-deduped (MatchResult.consumed). Exposed to the build program as the well-known consumed List; merge_blocks folds it into the produced block.
clean rejection(spec §10.7) A build that rejects — via reject when, an expression fault, or a failed merge — consumes nothing, has no side effects, and leaves the anchor available to later matchers. Walker returns [].
produced blockThe generic Block(btype, data: Dict) a successful build makes (the "G11" canonical product — never a subclass). Invisible to the pass that made it, visible to later matchers.
twinA scratchpad Python script that drives the real Python engine and prints the same canonical dump as a C++ mode, so diff gates the layer. Never committed.
gateA language-neutral verification a layer must pass (diff 0, or N/N vectors) before the next layer starts. Listed with exact commands in plan §1; never allowed to break silently.
unrunnable / skipA matcher whose match phase would consult a host predicate C++ can't yet supply, or whose build needs an unported binding. Computed from the artifact (both sides), emitted as SKIP lines — so the skip set itself is A/B'd.
