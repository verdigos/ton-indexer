10 · The production path (Phase G) — shadow mode, and what it does not yet prove

Everything so far ran the engine over .lz4 fixtures from a CLI. This chapter is the other end: the same library TUs running inside ton-index-postgres, on real ParsedBlock data, once per masterchain seqno. Three adapters make that possible — SchemaTraceLoader (production schema::Transaction -> the engine's own Trace structs), ParsedBlockLookupSource (the pipeline's in-block interface map -> lookup kind(key)), and MchClassifierActor (a thin td::actor gluing them to ClassifyCore). Nothing downstream changed: to_tree, init_block, MsgParse and classify_trace are byte-for-byte the code the gates already proved. The mode is SHADOW: fire-and-forget, log-only, zero DB writes, zero effect on the pipeline's promises. The offline proof that the adapters are faithful is a fourth gate pair, --classify-prod / --actions-prod, which diffs the full production path against the fixture path over the whole corpus — with one honestly-named hole (the nft family) that fixture floats make un-gatable offline. By the end you should know exactly which claims about production are proven, which are proven-by-construction, and which are still waiting on a remote shadow run.

Shadow mode: the contract

Phase G's rollout decision was made up front and it shapes every file on this page: the C++ engine runs BESIDE the authoritative classifier, not instead of it. It reads the ParsedBlock the interfaces stage just produced, classifies, and prints. It writes nothing, returns nothing, and cannot fail a seqno.

That constraint is what makes the wiring boring on purpose. There is no promise, no batch, no insert path, no _classifier_tasks bookkeeping — those all belong to the flip, not to shadow. Everything genuinely interesting in this chapter is therefore about FAITHFULNESS of the input adapters, not about output.

The library boundary was drawn one wave earlier: mch-classify is a static lib containing the pipeline TUs (loader, block tree, Value, IR, walker, host fns, build runtime, ActionBuild, ClassifyCore, parsers, the ABI pairs) plus the three Phase G adapters. The CLI exe links it and adds the harness TUs — dumps, vector runners, SchemaGate, main.cpp. ton-index-postgres links the lib only, so no harness code can reach production even by accident.

SchemaTraceLoader — production structs in, engine Trace out

The fixture loader (block-tree) reads msgpack into Trace / Transaction / Message / MsgContent. Production has a different shape entirely: schema::Transaction objects hanging off a ParsedBlock, with schema::Trace alongside. The obvious plan — walk schema::Trace — turns out to be wrong, and the header says why in its first paragraph.

schema::Trace carries only edges, no transaction list. And the engine's to_tree never used edges: it rebuilds the EventNode tree purely by message-hash linking (an out-msg hash of the parent tx equals the in-msg hash of the child). So the loader takes a plain std::vector<schema::Transaction> and the edges are simply unused. That single finding is what kept to_tree / init_block single-sourced and untouched.

What remains is a field-by-field map with three subtleties worth internalising: where aborted lives, why account strings get re-cased, and why message bodies are copied as already-serialized BOC strings.

ParsedBlockLookupSource — two tiers, one of them still a stub

lookup kind(key) is the engine's only way to ask about on-chain state it cannot see in the trace (build-programs). Offline it is served by FixtureLookupSource, reading the interfaces dict bundled in the .lz4. Production has to serve it from the pipeline.

The honest complication, answered by the lead's Q2 investigation: ParsedBlock.account_interfaces_ only covers accounts TOUCHED in this seqno, while the Python classifier's interface_repository reads DB/kvrocks and can resolve an interface detected months ago — a counterparty jetton wallet that this block never touched, say. The fixtures happen to bundle exactly such historical data, so the offline corpus does not expose the gap. Hence a two-tier design: tier 1 is the in-block map, tier 2 is an injectable hook for a DB/kvrocks round.

Read the class header (lines 1-21, not excerpted) for the per-kind table. The short version: five kinds resolve from tier 1 (jetton_wallet, nft_item, nft_sale, nft_auction, dedust_pool), and two are TIER-2-ONLY — nominator_pool has no V2 interface variant at all, and jvault_assets needs raw account-state cells plus chained reads that live in account_states_, not in the interface map. In production today the tier-2 hook is unset. That is the largest remaining gap before flip, and the telemetry below exists to size it.

MchClassifierActor — startup prep, per-trace run, failure taxonomy

The actor itself is thin by construction: group, load, classify, log, stop. Two things in it deserve real attention — where the engine's startup checks happen (this is also where the ABI bridge rows enter the production path), and how transactions are grouped into traces.

load_engine_prep is the embedding entry point, called once from main.cpp before the scheduler runs. It performs the same advisory registry validation the CLI does, loads the IR artifact, and builds the ClassifySetup (runnable matchers, skip table, generated build-fn map, referenced lookup kinds). A table/fn mismatch is returned as an error so the caller can be startup-fatal.

That validate_registries() call is the only place the ABI/tolk toolchain touches this chapter: the three parser sources (hand, schema-generated, ABI) merge into one flat name space, and a duplicate key must stop the process rather than resolve to whichever source enumerated first. The mechanism is covered in parse-layer; the tolk side — declarations, generated from_slice, the value-universe split — gets its own tutorial and is deliberately out of scope here.

The offline proof: --classify-prod / --actions-prod

None of the above can be gated by running the indexer, so the harness fakes the production input instead. SchemaGate.cpp loads a fixture the normal way (path A), SYNTHESIZES schema::Transaction objects back out of the loaded structs, feeds them through SchemaTraceLoader (path B), and — for the -prod variants — also synthesizes an account_interfaces_ map of real BlockchainInterfaceV2 structs and serves lookups through a real ParsedBlockLookupSource. Both paths then share run_dump's rendering and engine loop verbatim, so any difference in the diff is the adapter's.

The reverse synthesis is harness-only scaffolding and lives nowhere near the lib. The tier-2 hook in the gate is wired to a FixtureLookupSource over the same fixture interfaces (GateProdLookupSource, lines 256-286) — that is the gate standing in for the DB/kvrocks round production has yet to implement.

Four modes exist: --classify-schema / --actions-schema vary only the trace loader; --classify-prod / --actions-prod vary the loader AND the lookup source. Diffed against --classify / --actions the expectation is exact zero, and it holds across the whole corpus.

What remains before the flip

Shadow mode is wired, gated offline, and never run against live data. The worklist that stands between here and writing rows, in rough order of weight:

1. A REMOTE SHADOW RUN on a bounded dev seqno range — the only thing that produces real numbers for the tier-2 hit rate, the failure-category mix, and the cross-seqno fragmentation described above. Nothing offline can substitute for it. 2. The tier-2 lookup fallback (DB/kvrocks). Until it exists, nominator_pool and jvault_assets never resolve and historical interfaces are invisible; a shadow diff against Python-written rows will show deficits that are this, not the engine. 3. Trace gathering across seqnos — decide whether the actor waits for trace completion or the caller gathers. 4. Persistence itself: ClassifyResult.actions -> InsertBatchPostgres with ON CONFLICT DO NOTHING, plus cleanup-on-reprocess by trace_id, plus the _classifier_tasks bookkeeping inventory. ActionBuild already produces the rows (actions); nothing calls it from the actor. 5. Explicit matcher priorities in the specs (the artifact currently leans on file-name ordering) and the nft_purchase fill, which is blocked on corpus coverage.

Also worth carrying forward: the basic-actions fallback (ClassifyResult.fallback_actions) is ported but DORMANT — no corpus trace fails, so it is ungated. Shadow mode on live data is where it first gets real input, which is another reason the remote run is the gating item.
