5 · Matching — Walker, try_build, prefilter

This is the heart of the engine: the code that decides WHICH matcher fires on WHICH block. After this chapter you can read a .mch matcher's IR node graph (ir-artifact) and predict, without running anything, which blocks it will consume, which captures will bind, and why running it a minute later in the matcher order would give a different answer. Two loops do all the work: an OUTER loop that walks the block-tree spine once per matcher in priority order, and an INNER recursion (MatchState::match_node) that walks the matcher's node graph against one candidate block. The outer loop mutates the tree (each successful build merges blocks into a composite); the inner walk never does — it is pure, rollbackable, and re-runnable, which is exactly what makes --match a usable debugging tool. Two things trip up readers coming from the Python classifier: the B1 anchor prefilter (a per-trace opcode/btype inventory that skips whole traversals, and that must GROW as matchers produce new btypes or it would silently break composition), and the fact that value_flow does not exist on this side at all — the flow construct was removed from the language, so nothing in the match or build path accumulates account value flows.

Two loops, one tree

Start with the file banner. Walker.h states the contract that everything else on this page depends on: the match phase NEVER mutates the block tree. That is not an implementation detail — it is what makes every matcher in a run see the same tree state as its predecessor left it, and it is what lets --match probe all 33 matchers against every block independently.

Every captured run below was taken from S:/Dev/ton-indexer-clear/indexer with $ENGINE = ../ton-index-worker/cmake-build-debug-visual-studio/ton-mch-engine/ton-mch-engine.exe and $IR = ../ton-index-worker/ton-mch-engine/ir/mch_ir.json; the corpus is the 148 .lz4 fixtures in tests/traces.

The outer loop is in ClassifyCore.cpp. Read it next to the Python event_processing.py loop you already know: same shape (for each matcher, BFS the spine, try_build on each block), with two additions — the parent == nullptr guard and the B1 prefilter. The tree DOES mutate here, mid-walk, because a successful try_build merges blocks into a composite; the BFS reads cur->next_blocks only AFTER try_build has run on cur, which reproduces Python's generator-resume order exactly.

The anchor: prefilter, test_self, and the conservative-superset argument

matcher_test_self is the cheap "could this block possibly be my anchor" test — the direct port of Python's BlockMatcher.test_self. B1 sits one level above it: instead of asking that question for every (matcher, block) pair, ask it once per (matcher, trace) against an inventory of what the trace contains at all.

The correctness argument has to be airtight, because a wrong skip silently loses actions. It rests on two asymmetries. Opcodes are STATIC: produced composite blocks carry no opcode, so the opcode set can only shrink as matchers consume blocks — and the inventory is never shrunk, making it a superset. Btypes GROW, which is unsafe in the other direction, so produced btypes are folded back after every matcher. Blocks that get consumed are never REMOVED from the inventory, so the worst case is a traversal that runs and finds nothing — never a traversal that was wrongly skipped.

Pred anchors opt out entirely (prefilter = false): their test runs an arbitrary host predicate, not an op/btype comparison, so there is nothing to index. Mixed anchors never run at all — the loader keeps them unrunnable because the branch structure is not stored.

Order is the whole game: priority, registration order, consumption

Python's ordering lives in the hand-maintained matchers list in event_processing.py. Here it is data: a priority per matcher plus an optional registration_order permutation in the artifact, resolved once at load.

The resolution is: apply registration_order (default identity), then STABLE-sort by priority ascending. Stability is the tie-break — equal-priority matchers keep artifact order. In the production artifact today only three matchers carry an explicit priority (the jetton trio at 90); everything else defaults to 100 and therefore runs in artifact order. That is the entire ordering story, and it has real consequences you can watch in the dumps below.

Edges: child, children-set, parent, or

Four edge forms, four different semantics, and they are easy to conflate. In IR terms: child is a single node id, children is a list of node ids, parent is a single node id, and or is a node kind with a branches list. All four appear on the same node record and are evaluated in the order child → children → parent.

The pair to keep straight is child vs children. child accumulates: it tries the SAME node against EVERY successor and keeps all that match — one matcher node can bind many blocks. children is a bag-assignment: each declared item takes the first successor it fits and REMOVES it from a working copy, so two items can never claim the same block. Overlap between the two phases is legal because consume() dedupes by identity.

Recursion: frontier walk and cyclic descent

Two strategies share one node kind. frontier (9 of 11 recursive nodes in the prod artifact) is an iterative walk: try the exit first on each candidate, else take one step, then rebuild the frontier from what that step consumed. cyclic (2 nodes) is not iterative at all — the node graph itself contains back-edges, so recursion is ordinary match_node descent bounded by tree depth.

The frontier loop has three rules that surprise people. Exit is tried FIRST per candidate (so a pattern whose exit shares a prefix with its step will terminate early — the reason tonco_swap uses cyclic instead). Only ONE step is taken per round, then the frontier is replaced. And frontier exhaustion succeeds iff at least one step landed, REGARDLESS of whether an exit was declared — a declared exit that never fires does not fail the recursion, it just leaves its captures empty.

where_expr — the only expressions the match phase runs

Matching evaluates exactly one kind of expression: a node's inline where (expr), against one candidate block. Everything else — parse, lookup, host fn, let, out — is build phase (build-programs).

Two details matter for reading specs. First, a fault is not an error: eval_where collapses faulted, non-bool, and false into a single false, so a where clause that trips over a missing field simply does not match. Second, the interpreter's scope model is a single copied frame per comprehension — map(xs as e => …) binds e into a COPY of the environment, so the element variable shadows for the body only and never leaks. And parse as an expression is explicitly unreachable in the interpreter, which is another way of saying a where clause can never parse a message body.

try_build: produce, merge, aux — and the flow construct that is not here

try_build is where a match becomes permanent. It is also where four different things can decline, all of them cleanly: a structural mismatch, a build-program reject when, a failed merge, and (upstream) an anchor that already has a parent.
