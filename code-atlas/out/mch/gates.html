Gates and twins — verify everything yourself

Every claim in the previous eight chapters rests on one bar: run the C++ engine and the Python engine over the same corpus with the same artifact, and the two stdout streams must be byte-identical. Not "equivalent", not "same count" — Compare-Object returns zero lines. This chapter is the empowerment chapter: it shows the four kinds of gate (self-contained ctest modes, differential A/B twins, path-equivalence diffs, and generator repro guards), what each one actually proves, and the exact commands to run them. The twins are real Python — they import the production classifier (mch_ir engine, block_tree_serializer, the post-process passes), so a twin passing means the C++ engine agrees with the real Python mch runtime and serializer code — over the PORTED spec set. It does NOT mean agreement with the production event_classifier pipeline, whose old-engine matchers cover protocols mch has not ported (see the coffee-trace example in actions) today, not with a reimplementation of it. Two shared files keep the two sides from drifting silently: twins/cpp_surface.json (emitted by the engine itself) and twins/twin_registries.py (one factory list for all three twins). After this page you can check any number in this tutorial yourself, and you should — the numbers quoted in docs/mch-cpp-plan.md §1 are a dated snapshot and are already stale.

The twin philosophy: byte-diff-0, and why the dump is buffered

A twin is not a test fixture. It is a second implementation of a dump mode, written in Python, that imports the REAL classifier — indexer.events.mch_ir for the engine, block_tree_serializer.block_to_action for Action rows, post_process_dedust_liquidity / unwind_deployments for the host passes. So the gate is not "does C++ match a spec I wrote down" but "does C++ match the real Python mch engine and the serializer code it shares with production" — scoped, as always, to the PORTED spec set. That is why the twins were moved out of session scratchpads and committed: they encode gate semantics (canonical sorting, field-keyed cellhash renders, skip tables) that cost more to reconstruct than to keep.

Four twins, four engine modes, one comparison operator. Each twin's module docstring is the format contract from the Python side; the matching C++ header carries the same contract from the other side, and neither may change without the other.

The dump being byte-comparable at all depends on a property of the core: results are BUFFERED per trace and emitted only after the post-process passes have run. Nothing is printed mid-pipeline, so a trace that faults halfway does not leave half a dump behind — it emits exactly one TRACE_FAIL line on both sides. That atomicity is what makes the diff a clean signal instead of a cascade.

One twin up close: py_classify.py

py_classify.py is 306 lines and worth reading end to end once; it is the shortest complete statement of what the C++ engine is supposed to do. Three parts carry all the subtlety: what it imports (nothing hand-mirrored), how it decides which matchers are runnable, and the loop — which deviates from event_processing.py in exactly one documented way.

The render functions in the middle of the file (render, _cellhash, _render_field) are the value-rendering contract from value restated in Python; the cellhash: treatment of BOC-container fields is the §12 root-hash bar, which exists so that a payload cell compares by its root hash rather than by a serializer-dependent byte encoding.

Two shared files: the surface and the registries

Both engines have to agree on facts that are not in the IR artifact: which message parsers exist, which host predicates and fns are registered, which lookup kinds are servable, which fields are BOC containers. The C++ side owns those registries. Rather than mirror them by hand in Python (the original design, which drifted), the engine emits them.

Self-contained gates: vectors and ctest

The A/B twins need Python, the corpus, and a venv. The gates in this section need none of that — they are engine modes over version-controlled JSON documents, wired into CTest so ctest -R mch runs all eight in under a second. That is deliberate: the differential gates stay OUT of ctest precisely because they have external dependencies, and a test suite you cannot run from a cold checkout is a test suite people stop running.

The three vector families cover the three layers the twins cannot isolate. Expression vectors are run TWICE — once through the tree-walking interpreter and once through the generated C++ — against the same expectations, which is how the "one semantics" rule (interpreter and codegen call the same rt_* functions) is actually enforced rather than asserted. Build vectors do the same for statements, with expectations GENERATED by running the real Python BuildProgram.run rather than hand-authored. Message vectors are boundary cases emitted by the schema compiler next to the parsers it generates.

Repro guards: nothing generated is hand-edited

Three of the artifacts these gates depend on are generated: the IR artifact (Python ir_emit), the message-parser TU plus its vectors (Python msgs_gen), and the ton-abi C++ pairs (ton-abi-gen). A generated file that someone "just tweaked" would make every downstream gate lie — it would still be green, and it would be green about the wrong thing.

So each generator has a byte-repro guard: regenerate into memory or a temp dir, compare bytes with the committed copy, fail on any difference. Same discipline, three places. The --surface mirror gets the same treatment for the same reason.

The gate table, and why you should not trust its numbers

indexer/docs/mch-cpp-plan.md §1 is the canonical list: twelve rows, each a gate with an exact command and a Pass column. It covers the Python suites, the two expression-vector paths, build vectors, the shape/self tests plus ctest, the four A/B twins (msg parsing, match walker, classify, action rows), the schema-loader and prod-path equivalence gates, and codegen determinism. Its ground rules are equally load-bearing: run the full set before starting a task and again after finishing; a task is not done while any gate is red; Python is ground truth; and when codegen disagrees with the interpreter, codegen is wrong.

What you should NOT take from that table is its numbers. It is dated 2026-07-11 and says 147 fixtures, 196 classify actions, 196 Action rows, 97 expression vectors, 35 build vectors, ctest 5/5. Every one of those has moved: the corpus is 148 fixtures, classify and actions are 199 each, expression vectors 115, build vectors 38, message vectors 44, ctest 8/8 for mch plus 2/2 for ton-abi. All verified by the runs above, on this checkout, today. The commands in the table are stable; the counts are a snapshot, and the habit worth forming is to re-derive them rather than quote them.

One more honest gap, restated: the corpus contains no failing trace, so ClassifyResult::fallback_actions and the TRACE_FAIL path are exercised by neither twin. Byte-diff-0 is a very strong claim about the paths the corpus reaches, and says nothing about the ones it does not.
