1 · The engine in one pass — a trace becomes an action

After this chapter you can take any fixture in tests/traces, run it through the C++ engine, and say which matcher fired, why, and where every field of the resulting Action row came from. We follow ONE real trace — 03RZCW7mu3eJp-FWifVzKsRHafUrqQNu4E6YwZxvXJ0=.lz4, 5 transactions, 5 leaf blocks, exactly 1 action — end to end: LZ4+msgpack fixture -> Trace -> EventNode tree -> Block spine -> the one matcher whose anchor opcode is present -> captures -> a 6-field build output -> an Action row. You also see the same matcher in its two committed forms, the .mch source a human writes and the compiled row the runtime actually executes, and you learn the one discipline that holds the whole port together: the C++ dump and the Python twin must be byte-identical. Everything here is deliberately shallow — each stage is one chapter later on, and this page is the map you hang them on.

Lab setup — three commands

Keep a shell open at S:/Dev/ton-indexer-clear/indexer for the rest of the tutorial. Two paths never change, so export them once: the engine binary …/cmake-build-debug-visual-studio/ton-mch-engine/ton-mch-engine.exe and the IR artifact …/ton-mch-engine/ir/mch_ir.json. -T takes either a single .lz4 or a directory (which it walks sorted, .lz4 only).

The three commands you will use constantly:

1. ton-mch-engine -T <fixture> — no mode flag. Decodes the fixture and prints the transaction list plus the initialized block tree. This is the ONLY mode that spins up a TON actor scheduler; every --… mode returns from main before reaching it, single-threaded and deterministic, because their stdout is a compared artifact. 2. ton-mch-engine --classify -I <ir> -T <fixture|dir> — the whole match+build+merge pipeline, one ACTION line per produced block. 3. ton-mch-engine --actions -I <ir> -T <fixture|dir> — the same pipeline, but each produced block is serialized into a database Action row before printing.

Everything on stdout is byte-compared against a Python twin; anything advisory (orphan-node warnings, registry complaints) goes to stderr. When you pipe engine output anywhere, 2>/dev/null is usually what you want.

The fixture, and why this one

The corpus is 148 .lz4 fixtures producing 199 actions. Most are jetton/DEX traces with 20+ transactions and several interacting matchers — bad for a first read. 03RZCW7mu3eJp-FWifVzKsRHafUrqQNu4E6YwZxvXJ0=.lz4 is the smallest trace in the corpus that still exercises a genuinely non-trivial matcher: 5 transactions, 5 leaf blocks, exactly one action, and the matcher that produces it (vesting_send_message) is a two-node chain with a real message-body parse and a fully declarative 6-field build. Nothing about it is a special case — no lookups, no host shapers, no post-processing, no merge of a composite into another composite — so every mechanism you see is the general one.

A .lz4 fixture is LZ4-frame-compressed msgpack, written by the Python indexer's recorder.py and read by tests/utils/trace_deserializer.py on the Python side. It is a whole trace: transactions, their in/out messages, base64 message bodies, and a root interfaces section — the per-account interface data that TestInterfaceRepository serves. The C++ loader decodes only the fields structural matching needs and ignores unknown keys, so fixtures recorded by a newer recorder still load.

EventNode tree, then the Block init spine

Two structural steps happen before any matching, and both are straight ports of the Python substrate you already know: to_tree (from blocks/utils/tree_utils.py) links transactions into a message tree, and init_block (from event_processing.py) turns every node into exactly one leaf Block — ton_transfer, call_contract, or tick_tock — connected in the same shape.

Our fixture's tree, from the lab run above: the ext-in wallet tx becomes call_contract 0xcfc2d330, its child is call_contract 0xa7733acd (owner -> vesting request), and that node has two children — the outgoing ton_transfer the vesting contract forwards, and call_contract 0xf7733acd, the response callback. Five leaves, one root. The deep dive on ordering, merging and the deliberate deviations from Python lives in block-tree.

1L38–40Read this comment twice. 2L52–63lt() is the sort key for the entire spine (next_blocks is kept in min_lt-ascending order), so its fallback chain is load-bearing: tick-tock uses the transaction's lt, everything else prefers created_lt and only falls back to tx_lt. Thirty lines, and every one of them shows up in the output you already saw. Two opcode constants, a two-node chain, a parse, and six output fields. The --match run below stops after the match phase, so you can see the captures before any building happens.

1L2–5"The response is consumed … but only the request feeds the build" is the single most important invariant on this page. Matching a block does two independent things: it may bind a capture the build reads, AND it removes the block from the spine so no later matcher can claim it. The response capture exists purely for the second effect.
2L12–13opcode declarations are spec-local names. Nothing downstream knows the identifier — the compiled artifact carries only the number, in decimal. Grepping mch_ir.json for A7733ACD finds nothing; grep 2809346765.

4L19The chain arrow walks the BLOCK tree's next_blocks, not the message tree. In this fixture 0xf7733acd happens to be a direct child of the anchor, but the walker's reachability rules (matcher-runtime) are what actually decide, and they are not simply "is a child".

…and the same matcher, compiled

ir/mch_ir.json is the committed compilation of every .mch file — one JSON document, 11.5k lines, produced by the Python frontend (indexer/events/mch/) and consumed by both engines. It has three top-level parts that matter here: matchers (one row per matcher), nodes (a FLAT array of match-tree nodes shared by all matchers and referenced by index), and registration_order (the priority order matchers run in). Our matcher is matchers[32].

Read the row next to the spec above and the mapping is one-to-one. The point of showing both is that they are the same object: nothing is inferred at runtime, and if you ever wonder what the engine will actually do, this file — not the spec — is the answer. ir-artifact covers the format properly.

Mode dispatch and the core/harness split

main.cpp is a flat option parser followed by a chain of early returns. Every mode is a run_* free function that owns its own lifecycle; nothing is shared but the parsed -I / -T values and one startup check (validate_registries(), placed ahead of dispatch so even the self-test modes get it — see parse-layer).

Underneath, the code is split in two on a hard line. ClassifyCore.{h,cpp} is the PURE pipeline: (TraceContext + LoadedIr + LookupSource + generated build table) -> a buffered per-trace result, with no stdout, no filesystem, no fixture knowledge and no rendering. Classify.cpp is the harness that prints. That split is what lets the production actor reuse the identical pipeline (prod-path) and, more immediately, it is why a diff between --classify and --classify-prod can only come from the loader or the lookup source, never from the matching.

The loop that actually runs it

classify_trace is a port of the Python event_processing outer loop, and its shape is worth memorizing because every later chapter plugs into it: FOR EACH matcher in priority order, do a full BFS over the spine and try to build at every block. Not the other way around. That ordering is why the global matcher list order matters in the Python engine and matters identically here — an earlier matcher consumes blocks a later one would have wanted.

After every matcher has had its pass, host-side post-processing runs over a flat snapshot of the spine. Those passes are not expressible in the DSL (they merge across matcher results), so they stay hand-written on both sides.

diff-0 — the discipline behind every claim on this page

The C++ engine is a PORT, and the thing that makes a port trustworthy is not tests of the port's own opinions — it is running the same artifact through the original and demanding identical bytes. twins/py_classify.py runs the real Python IR engine (the same build_matchers + event_processing outer loop) and prints the exact same line format. So the correctness statement for the entire pipeline is a diff returning nothing.

1. **Know the corpus baseline.** The run below is the first thing to check after any change: 148 fixtures, 199 actions, and zero SKIP lines. Any page — including this one — that quotes different numbers is out of date.
