Build programs — expressions, captures, host seam

Matching (matcher-runtime) answers "does this shape occur here" and hands back a set of captured blocks. A build program answers the second half: "what does it MEAN" — it turns those captures into the produced block's data dict, its failed/broken flags, and (for a switch matcher) its btype. After this chapter you can read any .mch build program and predict exactly what the engine does with it: which statements can reject a match, where a null quietly propagates and where it faults, what parse actually guarantees, when the engine calls out to a hand-written C++ host fn, and why the C++ and Python engines cannot drift apart on any of it. You will also be able to read the GENERATED C++ that the engine really runs — build programs are not interpreted in production; mch-codegen emits one straight-line BuildOutcome build_<n>(BuildEnv&) per matcher whose only job is to call the rt_* leaves documented here. The one thing this chapter does NOT cover is what happens to the produced block afterwards: merging into the tree is block-tree, serialization into Action rows is actions.

What a build program is

A .mch matcher has two halves separated by a blank line: a PATTERN (chapter 5) and, below it, a build program. The build program is a short imperative script over the captures the pattern bound. Its whole statement vocabulary is: parse CAP as T1|T2, let NAME = expr, reject when expr, failed when expr, broken when expr, out { field: expr }, and produces switch { when expr => BTYPE out {...} … else => … }.

Two properties make it tractable. It is STATELESS — nothing survives between runs, and the program is re-run from scratch for every matched anchor in the trace. And it is TOTAL in one direction only: every statement can reject the match, none can crash it. Any evaluation error anywhere (a missing object field, an un-orderable comparison, an unregistered lookup kind) becomes a clean rejection of this match, indistinguishable from the pattern not having matched at all.

The execution model: stateless, per-matched-anchor, codegen'd

Nothing in this layer interprets a build program in production. mch-codegen --builds reads the IR artifact and emits one C++ function per matcher into the build tree; the engine holds a table of those function pointers keyed by artifact index. The generated code contains no policy — every operation is a call into BuildRuntime/ExprRuntime, so the interpreter path (ExprEval, used by the conformance vectors) and the production path cannot diverge on semantics.

The two structs below are the entire interface between generated code and the engine: BuildOutcome out, BuildEnv in.

parse: the statement, the expression, and the contract

parse CAP as T1|T2 is soft by design. Its inner half (soft_parse, first alternative that succeeds wins, all-fail ⇒ Null body) is excerpted in parse-layer; here is the outer half — what a parse statement does with the target it is given, and how .body reads the result back.

The key asymmetry to hold onto: an UNREGISTERED type name is a fault (broken spec), a failing PARSER is not (normal traffic). Everything else follows from that. And because a failed parse is silent, the op-guard rule from parse-layer is not optional discipline — it is the only thing standing between an ABI-path parse and a divergence that surfaces hundreds of lines away in a twin diff.

Lookups: why the build fn runs more than once

lookup kind(args) reaches outside the trace — jetton wallet interfaces, NFT items, pool records. In Python that is an inline async call. In C++ the fetch has to be batched (production issues one actor round per trace, prod-path), so the build fn is executed as a DRY pass against a table that records misses, the misses are fetched, and the fn is re-run against a filled table. The build program being stateless and side-effect-free is exactly what makes running it twice legal.

One subtlety forces a loop rather than a single dry pass: a lookup whose ARGUMENT comes from another lookup. On the first pass the inner lookup returns Null, the null-strict rule short-circuits the outer call, and the outer key never forms. So the collect pass is iterated to a fixpoint.

The host seam: preds, fns, shapers

Some logic genuinely cannot be written declaratively — reconstructing roles from an unordered consumed set, walking a DeDust step chain, scanning for a per-hop event. Those stay as hand-written C++ registered in one of three name→function-pointer maps. The names are the PYTHON registry keys, so a .mch spec compiled by the Python frontend and executed by the C++ engine resolves the same identifier on both sides.

The three registries differ in when they run: predicates at match time (chapter 5), fns during the build program, shapers AFTER the produced block has merged its consumed set. What actually runs: the skip table

build_skip_reason is the function that turns "this C++ engine implements a subset" into a precise, comparable statement.
