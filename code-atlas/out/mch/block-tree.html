3 · From trace to Block tree — the structure matchers walk

Chapter 1 showed a trace turning into an action; chapter 2 showed the Value that travels through it. This chapter is the substrate in between: the four plain structs a fixture decodes into, the EventNode tree that reassembles the message graph from flat rows, and the Block spine that init_block lays over it. By the end you can read any block-tree dump and say exactly which C++ line produced each node, predict what failed will be for a given transaction, and know precisely what a merge inherits and what it destroys. This layer is a port of the Python indexer's tree_utils.to_tree / core.Block / event_processing.init_block, and it is the one layer that was verified byte-identical against Python across the whole fixture corpus — so most of what is worth saying here is about the places where the C++ deliberately does NOT copy Python (determinism) and the places where it copies Python bug-for-bug (failed semantics, ContractDeploy children). Nothing in this file matches anything: it only builds the shape that matcher-runtime walks.

The fixture loader — msgpack in, four structs out

TraceLoader.{h,cpp} is the FIXTURE path only: it reads one tests/traces/*.lz4 (an LZ4 frame wrapping msgpack, written by the Python recorder) and produces Trace -> Transaction -> Message -> MsgContent. The production loader that reads the same shape out of Postgres is a different file entirely and is covered in prod-path; everything downstream of these four structs is shared, which is exactly what makes the prod A/B gate meaningful.

The decode is deliberately dumb: every field is fetched by name, a missing or nil key yields the default, and unknown keys are ignored. There is no schema validation because the fixture writer and this reader are pinned together by the twin gates, not by a contract. Two decisions in here have consequences much later — the signed storage of opcode, and the fact that message_content is optional.

to_tree — parent links by message hash

A trace arrives as a flat list of transactions. to_tree rebuilds the message graph with one trick: sort the transactions by lt DESCENDING, so every child transaction is created before the parent that sent to it. By the time a parent enumerates its out-messages, the in-msg-hash -> tx-hash map already contains the child's entry, and the link is a single lookup. This is a direct port of Python's tree_utils.to_tree, sort direction and all.

The node type is deliberately thin — a message pointer, a transaction pointer, a tick-tock flag, and links. Everything derived (lt(), opcode(), tx_hash()) is computed on demand so there is no cached state to get stale when a block absorbs nodes from elsewhere.

What a Block is

A Block is a node in a second tree laid over the first. Initially there is one block per event node (the "spine"), and matching replaces runs of blocks with produced blocks that own them. Two link families coexist and must not be confused: next_blocks/previous_block is the FLOW (who follows whom in the message graph), and children_blocks/parent is CONSUMPTION (who was absorbed into whom). A matcher walks the first; the serializer in actions reads the second.

The file header is worth reading before the struct, because it enumerates every place the C++ deliberately departs from Python. All four departures are in the same direction: replace a Python set() or an unsorted list with a deterministic order.

init_block — the leaf spine

init_block walks the event tree and hangs exactly one leaf block off each node. There are four leaf btypes: tick_tock, ton_transfer, call_contract, and contract_deploy — but the fourth is never a spine node, it is a side-effect block pushed into a leaf's children_blocks.

The classification rule is three lines long and the failed rules are longer than the classification. That is the honest shape of this code: what a block IS is trivial, whether it FAILED is a pile of protocol-specific exceptions that the Python engine accumulated over years, and every one of them had to be copied exactly.

merge_blocks — who inherits what

When a matcher accepts, the produced block calls merge_blocks(consumed) and the spine is rewritten in place. This is the only destructive operation in the substrate, and the header comment states the contract bluntly: it must be called ONLY after a build accepts, because there is no rollback. The false return exists for the one case that can be detected before any mutation — no earliest common block — and in that case the tree is untouched.

Four helpers do the work. ensure_earliest_common_block picks the anchor and validates that the consumed set is actually connected. find_frontier computes what the produced block should now point at. compact_connections repairs the parent's outgoing edges. calculate_min_max_lt re-derives the ordering key. Read them in that order.

1L47–50Sort by POINTER, unique, then stable-sort by min_lt. The pointer sort is not cosmetic — it is how HostCoffee's original code deduped, and reproducing it (rather than a first-seen dedup) is what keeps peer-swap order byte-identical. This is the one place in the substrate where address order is deliberately observable, and it is safe only because the second sort is stable on a key that ties rarely.
2L53–57bool(block.data[field]) for exactly the two carriers the specs use. Note what is FALSE here: a missing key, a null, a string, an Amount. Python's bool() would say a non-empty string is true — the narrow reading is intentional, because every real call site tests a bool or an int flag and a wider rule would silently change behaviour if a field's type ever moved.
3L59–63AccountId(v).as_str() — and crucially addr_none returns nullopt, not an empty string. Callers gate on the optional, which is how an addr_none address stops a wallet lookup instead of performing one against the empty key. Contrast the ABI universe in parse-layer, where addr_none is a present-but-empty Account for the same TL-B input.
