4 · The IR — what the runtime actually executes

The C++ engine contains no matchers. It contains an interpreter for ir/mch_ir.json, a single 272 KB artifact compiled from the .mch specs by the Python frontend. After this chapter you can open that file and read it: you will know why a matcher record has both an anchor and a root, why nodes is one flat global array instead of a tree, what each of the six node kinds and six edge fields means, how maybe / ^ / <- / $rule in a spec turn into JSON keys, and why a key being ABSENT (priority, builder, shape) carries meaning. You will also know what IrLoader refuses to load and why each refusal exists — the loader is written fail-closed on purpose, because a silently-degraded artifact matches MORE blocks than the spec author wrote. The matcher half of what the loader produces is executed in matcher-runtime; the build_program half in build-programs. This chapter stops at "you can read it".

The artifact in one screen

Open ir/mch_ir.json and the first 33 lines tell you almost everything about its shape: a version tag, a provenance block nobody reads, and then two flat arrays. There is no nesting — a matcher points at nodes by integer index, and nodes point at each other by integer index. That is a deliberate wire format, not an accident of serialization: it makes the whole graph addressable by a stable id, which is what lets the C++ build step generate a function per (matcher, node) pair and pair it with the artifact by sha.

The file is regenerated, never edited. ir/README.md documents the one command; everything downstream of it (where_expr codegen, build-fn codegen, table sha pairing) is a CMake custom command.

One matcher, field by field

jetton_transfer is the first record in the artifact and the smallest useful one: three atoms, three nodes, one optional leg. Read the spec first, then the record, then the nodes — the three excerpts below are the same matcher three times.

A caution before you start: the spec you want is specs_decl/jettons.mch, not the same-named matcher in specs/jettons.mch. The manifest excludes the latter.

1L36–41anchor and root are two representations of the same head test, kept separate on purpose. The anchor is a PREFILTER — the walker only visits blocks whose opcode is in this set — while the root is the pattern's first node. ir_emit._anchor_record derives the anchor from the root when the compiler didn't record a distinct one, so they usually agree; the interesting cases are when they don't (next section).
2L42root: 0 indexes the GLOBAL nodes array. The loader immediately renumbers the reachable subgraph to local ids with root == 0, so the id you read here is not the id the C++ runtime uses — CompiledNode::global_id is what preserves the artifact id for the codegen table.
3L43–45produces is a LIST, not a string. Most matchers produce one btype, but change_dns produces three and tonstakers_withdraw two — the switch build statement chooses which at build time (build-programs). A reader who assumes produces[0] is the answer will be wrong twice.
4L46–59The captures table IS the slot numbering: position in this array is the slot id, and card (one/opt/many) is what the walker enforces on binding. A node's capture key is a NAME; the loader resolves it against this table and stores -1 for an unknown name rather than erroring — a capture typo is a silent no-bind, not a load failure.
5L60–62Absent keys are meaningful and that is the trap of this format. include_excess/include_bounces are always written; priority is written ONLY when it differs from 100; builder and shape only when present. So "no priority key" means 100, and the 30 priority-100 matchers simply omit it — you cannot sort matchers by reading m.priority without a default.

The node pool: six kinds, six edge fields

Every node record has a kind (one of contract, block_type, pred, any, or, recursive) and may carry up to six edge fields (child, children[], parent, branches[], step, exit) plus the modifiers optional, capture, where, where_expr, exclusive, strategy. In the production artifact the distribution is 208 contract, 64 block_type, 36 or, 11 recursive, 8 pred, 2 any.

Two of those numbers are worth pausing on. Only two nodes are any — and neither is a wildcard, as the first excerpt shows. Only 11 are recursive, but they carry the entire multi-hop-swap machinery.

Build programs and expression nodes — a preview

About 95% of the artifact by volume is not pattern at all: it is build_program, a flat statement list per matcher whose expressions are k-tagged trees. This chapter only teaches you to READ them; execution is build-programs and the parse statement's registry is parse-layer.

Statement tags in the production artifact: 32 let, 31 out, 29 parse, 27 reject, 18 failed, 2 switch. Expression tags: 600 attr, 512 name, 144 call, 107 bin, 98 null, 51 ternary, 17 unary, 13 str, 9 int, 8 lookup, 5 bool, 4 dotfield, and exactly one each of mapc, list, record.

IrLoader: what it refuses to load

IrLoader.cpp is 520 lines and roughly a third of it is refusal. That ratio is the design: the IR spec's §8.1 rule is that an unrecognized or missing field must never degrade into something permissive, because a permissive degrade makes a corrupt artifact match MORE blocks than the spec author wrote — and matching more blocks is silent, whereas failing to load is loud.

The exceptions are documented at their sites and worth memorizing, because they are the places where a corrupt artifact WILL load: priority absent defaults to 100, include_excess/include_bounces absent default to true, and strategy falls back to frontier for any unrecognized string (contrast parse_kind, which errors on an unknown node kind with the explicit comment that a typo must not become the permissive any wildcard).

Priorities and registration order

Two knobs decide which matcher gets to consume a block first, and they interact. priority (default 100, ascending — lower runs first) is the primary key; registration_order breaks ties. In the production artifact registration_order is the identity permutation, which means ties break on emission order: manifest file order, then source position within each file. That is the whole reason emit_manifest.json lists specs_decl/jettons.mch first and documents it in a comment.

What a matcher gets skipped for

Runnability is decided twice. The loader decides the MATCH half (predicates only). build_skip_reason decides the BUILD half by checking the artifact's collected ref_* sets against the live C++ registries — and this is the function that makes an unported protocol a visible SKIP line rather than a crash or, worse, a silently empty result.

A matcher with a non-empty skip reason is dropped from the run entirely, and the reason is printed once, sorted, at the top of every --match / --classify dump. The Python twin computes the same set from the same artifact, so the skip set is itself gate-checked (gates).

The emit side, briefly

You do not need the Python compiler internals to read the artifact, but you do need to know three facts about how it is produced.

First, the source list is ir/emit_manifest.json, and its order IS the registration order; frontend.source_files echoes it. Second, ir_emit.py emits node ids as a per-matcher DFS with a memo keyed on Python object identity — which is why cyclic recursion resolves to a back-edge rather than looping forever, and why node ranges are disjoint per matcher even though the array is global. Third, and most useful in practice: the emitter is byte-deterministic and a pytest holds it to that.
