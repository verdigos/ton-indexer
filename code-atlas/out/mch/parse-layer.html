Parse layer — 3 parser sources, 2 value universes

This layer turns a message body cell into an mch::Value that a build program can read as CAPTURE.body.field. It is a name -> function-pointer registry fed by three independent sources: 7 hand-written parsers, 22 compiled from mch-msgs.schema, and 3 that come out of the Tolk ABI toolchain. The first two sources are pytoniq-parity: they reproduce, deliberately and bug-for-bug, what the Python reference parsers in indexer/events/blocks/messages/ do — including skipping the leading 32 opcode bits WITHOUT checking them. The third source is tolk-faithful: the generated from_slice CHECKS the opcode prefix and models addresses the way @ton/core does. Those two conventions are incompatible in observable ways (a missing address is null in one and a present-but-empty Account in the other), and nothing in the type system keeps them apart — the discipline that does is the op-guard rule at the end of this page. The layer's whole correctness bar is an A/B twin gate: the same corpus through C++ and through the Python engine must produce byte-identical parse dumps.

The registry: three sources, one map, fail-closed

MsgParse.h is short but it is the contract for the entire layer — read its header comment before any code. The registry itself is a lazily-built std::map<std::string, MsgParserFn> where MsgParserFn is a plain function pointer (td::Result<Value>(*)(const td::Ref<vm::Cell>&)), not a std::function. That choice is load-bearing later: it is what lets an ABI parser register as an ordinary row with no closure state and no init API.

Three sources merge in a fixed order. Collisions are possible in principle (all three name-spaces are flat), so they are detected once at build time and refused twice: at startup by validate_registries(), and at every lookup by parse_message_body.

1L6–11This is the actual specification of the layer, not a courtesy comment. "no opcode validation: the first 32 bits are skipped unchecked" is what makes the pytoniq universe lenient: a body carrying the wrong opcode does not fail, it produces a plausible object built from the wrong bits. Safety comes entirely from the matcher having already checked op upstream, in the matcher runtime.
2L12–14addr_none becomes a NULL Value — not an empty address. On this path there is no representation for "present but empty"; a spec that wants to detect addr_none tests for null. Remember this line; the ABI path does the opposite.
3L15–17"conditionally-present keys" is a real part of the shape: the Python twin sets some attributes only on some code paths, vars(obj) is what gets compared, so C++ must omit the key rather than emit a null. The jetton sum_type excerpt below is the live case.
4L19–25The one exception, and the rule it forces. Because ABI parsers validate the prefix and their Python twins do not, an unguarded ABI-path parse gives a C++ error and a Python garbage object on the same body — the two sides diverge and the A/B gate fails. Universe 1 — pytoniq parity (PSlice and the hand parsers)

parse/PSlice.{h,cpp} is the leaf layer everything in sources 1 and 2 is built from: address, coins, snake-bytes, to-cell. It is not a thin wrapper over vm::CellSlice — it exists because pytoniq's Slice has behaviours a CellSlice does not, and the twin gate compares rendered output, so those behaviours have to be reproduced rather than corrected.

The rest of PSlice.cpp beyond the excerpt below is the same kind of work: load_snake_bytes (byte-aligned, at most one ref per link), pslice_to_cell, and a byte-level reimplementation of Python's bytes.decode("utf-8", errors="backslashreplace") used for TON-transfer comments. Read those directly if you touch comments; they are mechanical once the principle is clear.

Universe 1, continued — the schema-generated middle source

Most registered parsers are not written by hand. mch-msgs.schema is a small declarative file compiled by indexer/events/mch/msgs_gen.py into a committed C++ TU, MsgParsersGenerated.cpp. Two constraints make this safe rather than clever: the generator may only emit calls to leaf helpers that already existed and were already A/B-proven, and regeneration must be byte-stable (a pytest re-runs the generator and diffs the committed file).

The generated code lives in the SAME universe as the hand parsers — same leaves, same unchecked opcode skip. The schema is a compression of hand parsers, not a new semantics.

Universe 2 — the ABI bridge (entry to the tolk world)

The third source comes from a completely different toolchain: a .tolk declaration is compiled to dedust_v2.abi.json, which ton-abi-gen turns into C++ structs with from_slice / store / to_abi_value. Those structs know nothing about mch — the dependency runs mch -> ton-abi only, permanently.

AbiBridge is the whole seam: a function template that adapts T::from_slice to a MsgParserFn, plus a total AbiValue -> mch::Value adapter. Both halves are worth reading closely, because this is where the second value universe gets its shape.

Why the universes never mix: the op-guard rule

Both universes hand back an mch::Value, and the engine has no way to tell which one produced it. The rule that keeps them from colliding is enforced socially, in spec review: an ABI-path parse capture must be bound to a capture that is already op-guarded.

The reason is asymmetric failure. The C++ ABI parser CHECKS the prefix and errors on a mismatch; the Python twin skips 32 bits unchecked like everything else in the Python engine. On a body with the right opcode both sides agree. On any other body, C++ produces a parse failure (a Null body, silently) and Python produces a garbage object — and the A/B gate diverges, usually somewhere far away from the parse.

How a spec's parse statement actually resolves

The registry has one real consumer: the build runtime's parse statement (build-programs). Its behaviour explains why a mis-wired ABI parse is quiet rather than loud — a failed parse and a not-this-type parse are the same outcome by design.

There is also a preflight: BuildDriver scans every matcher's referenced message types against the registry and build-skips matchers whose types are missing, printing a warning listing them. So a spec referencing a type nobody registered degrades to "this matcher never builds", visible in the skip reasons rather than as a crash (ir-artifact, gates).
