Value — the engine's currency

Everything downstream of the trace loader speaks one type: mch::Value. A matcher's where expression, a parsed message body, a build program's capture, a host function's return, an Action column — all of them are Values, and every equality, render and null-check in this tutorial is a rule about this one struct. It is a hand-discriminated tagged union of 14 kinds with a deliberately Python-shaped semantics: unbounded integers (RefInt256, because jetton amounts overflow int64), an Amount wrapper that can be present-but-empty (Amount(None)), an Account that can be present-but-addr_none, and two different map kinds that differ only in attribute-access rules. Read this chapter for four things you will otherwise re-derive painfully later: why null and addr_none are not the same value (and why the two parser universes disagree about which one a missing address becomes), why Cell-derived fields are compared by root hash instead of bytes, why there are two equality functions rather than one, and why the VType enum may only ever be appended to.

What a Value is, and why the enum only grows

Value.h opens with the only design rationale you get for the whole model, and it is worth reading as a spec rather than as a comment: each bullet is a Python behaviour that had to be imported rather than improved on. The C++ side is a mirror of what indexer/events/mch/expr_eval.py produces, and the twin gates compare RENDERED values (gates) — so every place the two could disagree had to be decided deliberately, once, here.

The VType enum carries an unwritten rule that the design docs state explicitly: it is APPEND-ONLY. W12-BRIDGE-DESIGN.md §3 rejects a native external-address kind on exactly this ground — "Value.h VType enum is append-only and adding a member forces a clean engine-obj rebuild". The hazard is mechanical, not stylistic: several translation units in this engine are GENERATED into the build tree (wheres_generated.cpp, builds_ir_generated.cpp, …) and ninja will happily reuse their stale object files after a Value layout or enum change, producing a binary whose halves disagree about the struct — which shows up as heap corruption at runtime, not as a link error. Inserting a member in the middle of the enum is the worse version of the same bug, because generated code stores kind tags.

1L9–13Every expression integer is a 256-bit big-int, not an int64, and that is a correctness requirement rather than caution: Python ints are unbounded and a jetton amount routinely exceeds int64. Widening happens on entry (JSON numbers, host fields), so no arithmetic path in the engine ever has to think about overflow — but it also means num is a refcounted handle that can be NULL, and a null num is meaningful (see the Amount line in the kind list below, and make_amount_none).
2L14–18The distinction the rest of this chapter keeps returning to: Account has a third state besides "has an address" and "is absent" — present-but-empty (addr_none). 3L19–22A parity bug faithfully preserved: Python's Asset.__eq__ reads the jetton master's string BEFORE it checks the is_ton branch, so comparing a TON asset with a string raises instead of matching "ton". 3L53–55Amount is not a synonym for Int: it is a wrapper kind whose payload may be null (Amount(None)), and Account is not a synonym for Str. Both exist so that Python's wrapper types survive the round trip into the dumps — collapsing either one would make the twin comparison lossy.
4L61Float exists only because fixture data contains one (a GetGems price). Rendering is split too: BuildDriver prints float:<%.17g> (the line's "bare -> unrenderable" comment predates that), while describe() and --parse-dump still print ?. A dead end by design either way, not an escape hatch.

The struct: one flat bag, hand-discriminated

There is no std::variant here. Every kind's payload is a named member of one struct, and only the members relevant to t are meaningful. That is a deliberate trade — it keeps the type trivially copyable-ish and cheap to pass around, at the cost that nothing prevents you from reading str off an Int. When you read engine code, always check t first; v.str on the wrong kind is empty rather than wrong-looking.

The factories below are the ONLY sanctioned way to build a Value (plus the default-constructed null()), and several of them encode a contract that the struct itself cannot: make_account_raw takes an ALREADY-normalized string, make_amount_none deliberately leaves num null, make_amount_float sets a flag that makes the value un-usable in expressions.

Field access: Dict, Obj, and the .exit_code hop

Both map kinds store a vector<pair<string, Value>>, not a std::map. The reason is size, not order: field counts are tiny, so a linear scan beats a node-per-key tree and the whole Fields vector is a single allocation.

Insertion order is PRESERVED but almost nowhere observable. Every comparable render sorts keys — render_fields_sorted in ParseDump.cpp, the explicit key sort in BuildDriver.cpp, and sorted(...) in both Python twins — and neither equality function is order-sensitive (structural_equal and container_eq both compare key SETS). What genuinely sees insertion order is describe(), the positional assertions in DexRecordsTest.cpp (key_at(d, 0, "asset") and friends), and the ABI bridge's rule that "$" is emitted FIRST so a consumer can switch on .$ (W12-BRIDGE-DESIGN.md §3, Struct row).

The lookup itself is trivial; the interesting behaviour is one level up, in the expression runtime's rt_access, which is where the Dict/Obj distinction finally pays for itself.

Accounts, and the two meanings of nothing

An address enters the engine as text from three directions — a transaction account off the trace loader, a parsed message field, an address literal in a spec — and all three funnel through normalize_raw_address before becoming an Account. Canonical form is raw wc:HEX with UPPERCASE hex, matching Python's AccountId.as_str(). User-friendly base64 addresses are simply not a thing in this engine.

The important part is what happens to a MISSING address, because the two parser universes answer differently. On the pytoniq-parity path an addr_none in a message body becomes a NULL Value; on the ABI path it becomes Value::make_account_none() — a present Account with addr_none set (parse-layer). Both are correct for their own twin, and the run below shows the pytoniq answer landing in a real dump. A spec that null-tests an address field is therefore asking a question whose meaning depends on which parser produced it.

One more asymmetry worth internalising: the account() builtin FAULTS on a string it cannot normalize (and maps the literal string "addr_none" to make_account_none()), while the trace-side helper passes a non-normalizable address through unchanged rather than failing the trace.

Cells: the root hash is the currency

A Cell Value is a td::Ref<vm::Cell> and compares by root hash everywhere. The subtler rule is about cell-derived STRINGS and BYTES: a forward_payload that a parser serialized to BOC bytes, or a b64() builtin output, cannot be compared bytewise between the two engines — pytoniq and td produce different BOC containers (ordering, CRC provenance) for the same cell tree. Plan §12 resolves this by rendering such fields as cellhash:<HEX-UPPER> in every comparable dump.

The gate is by FIELD NAME, not by value type — is_boc_field("forward_payload") is true, is_boc_field("comment") is false — because comment, bitcoin_txid and pubkey are raw non-BOC bytes whose exact bytes ARE the data. That set is small, hand-curated, and exported to the Python twins through --surface so a name can never be in the set on one side only.

(td_boc_serialize, just above the excerpt, is the other half of the same decision: once dumps compare by root hash, container byte order stops mattering, so the engine uses td's deterministic native writer everywhere. The former pytoniq-order writer — and a P3 exponential-re-walk DoS in it — went away with that change.)

Two equalities, on purpose

There are two deep-equality functions over Value and they are kept apart deliberately. structural_equal (in Value.cpp) is the HARNESS comparator: it answers "does this actual value match the expected value from a conformance vector", and it is asymmetric — the EXPECTED value's type drives the switch. rt_eq → raw_eq → container_eq (in ExprRuntime.cpp) is the LANGUAGE's ==: symmetric, with cross-type rules (Account vs Str, Asset vs Str) that a harness comparator has no business having.

The file comment states the reasoning plainly: "the runtime owns its own container == instead of borrowing the harness comparator… The two are behaviourally equivalent for the value model today — this is a separation of concerns so structural_equal stays harness-only." Read that claim narrowly, because it is scoped to the CONTAINER walks — and those do agree. The GUARDS in front of them do not: eq_result faults on a float-backed Amount, and on TON-asset-vs-string, before raw_eq is ever reached, whereas structural_equal quietly accepts the first of those pairings. The separation is what lets a change to what a spec's == means avoid silently changing what a vector accepts. If you are reading match/build behaviour, rt_eq is the one you want (build-programs); if you are reading a FAIL line from --vectors, it came from structural_equal (gates).

Truthiness: there isn't any

Python's "empty list is false" has NO analogue in this engine. A matcher's where expression must evaluate to a genuine Bool that is true; the Walker's check is !r.faulted && r.value.t == VType::Bool && r.value.boolean, so a null, a zero Int, an empty List, or a faulted evaluation are all equally "did not match" (matcher-runtime). That single line is why null-propagation is safe: an expression that silently became null just fails the guard instead of throwing.

The one place a Python-ish truthiness is reproduced is inside a host function, over a block's data dict — and it is narrow on purpose.
