From blocks to Action rows

By the end of build-programs a matcher has produced a Block carrying a data dict. This chapter is the last leg: how that block becomes an Action row with an id, a time window, a tx-hash set, an accounts set, eight directional columns and one protocol-specific composite. Two files do the work. ClassifyCore.cpp runs the post-pass stage — the host post-processors (post_process_dedust_liquidity, post_process_stonfi_v2_liquidity, unwind_deployments) that mutate the already-matched block set, plus the per-trace exception boundary that decides between "commit these actions" and "throw them all away and fall back to leaf actions". ActionBuild.{h,cpp} is the block_tree_serializer.py port: build_action fills the universal fields, fill_action dispatches on btype to one of 21 fill_* functions. Rendering is NOT in either — render_action stays harness-side in Classify.cpp, which is the whole point of the core/harness split. Two things will surprise you if you know the Python classifier from another branch: there is NO role system on this branch (action_accounts is role-less by design, not by omission), and the A/B twin gate compares FULL rendered rows, so every field you see below is byte-pinned against the real Python serializer over 148 fixtures.

The seam: a CoreAction is not a row

The core deliberately stops one step short of an Action. What the matcher loop collects is a CoreAction: four raw pointers into the caller's arena, no strings, no rendering, no schema. Everything that turns those pointers into text or into a row happens in an adapter — the CLI dump in Classify.cpp, or the production actor in prod-path.

That sounds like ceremony until you notice WHEN a CoreAction is collected versus when it is rendered. It is collected at fire time, mid-walk, while later matchers are still mutating the tree; it is rendered after the post-pass, from the block's FINAL state. Keeping the two apart is what lets a later merge rewrite produced->data and have the row reflect it.

The post-pass stage: what survives becomes a row

After every matcher has walked, three host post-processors run over a freshly re-collected spine list. They are ports of blocks/liquidity.py and event_processing.py, and unlike matchers they are imperative surgery on the block graph: they merge two produced blocks into one, re-parent children, and delete blocks that already have a CoreAction pointing at them.

That last part is the mechanism to understand. A post-processor never touches pending; it inserts into a removed set, and the filter at the end of classify_trace is what actually drops the row. So "this matcher fired but produced no action" has exactly two causes on this branch: a clean rejection inside try_build (matcher-runtime), or a post-processor merging the produced block away here.

The failure fork

classify_trace wraps the whole matcher loop and post-pass in one try/catch. This is the C++ image of event_processing.py's per-trace boundary: a trace that throws anywhere loses ALL its classified actions and is re-run through a leaf-only classification instead.

The FailureCategory enum next to it is newer and serves a different purpose — shadow-mode telemetry for prod-path. It is worth reading its comment carefully, because it documents as much by what it refuses to enumerate as by what it does.

build_action: the fields every row gets

ActionBuild.{h,cpp} moved out of the harness in R1b so the production actor could call it without dragging stdout printing along. The code is byte-identical to what used to live in Classify.cpp — the twin dumps proved the move.

build_action fills what does not depend on btype: the action id, the lt/utime window, mc_seqno_end, tx_hashes, and accounts. Then it calls fill_action, and only if that succeeds does it assemble accounts — because accounts are derived from the directional fields the fill just wrote.

One honesty note about the demo trace used below (013-itRDy…): in PRODUCTION this trace is classified as coffee_staking_claim_rewards — the coffee staking protocol is NOT ported to mch specs, so the mch engine (both C++ and its Python twin, identically) classifies the ported jetton_transfer leg instead. The row is real and every column below is exactly what ActionBuild emits; it is just not what the production classifier stores for this trace. The twin gate proves C++ == Python-mch over PORTED specs — not C++ == the production event_classifier. See gates for the precise claim.

fill_action: dispatch, helpers, and two representative fills

Everything btype-specific lives in a fill_*. They all have the same shape: read block.data fields by name, run them through one of three converters, write directional columns and one composite dict. The converters are the interesting part — they are where the engine's rich Value types (value) collapse into the flat column types the DB expects.

One consequence worth internalising before reading any fill: render_value SORTS dict keys, so the order of f.emplace_back(...) calls is invisible to the A/B gate. The names and values are pinned; the emission order is not.

render_action is the piece that did NOT move lib-side, and the split is exactly where you would want it: everything above produces an Action value; this turns one into a line of text for the A/B channel. Production never calls it — it binds the same Action to SQL instead (prod-path).

The parity contract is stronger than it is for any other layer in this engine. twins/py_actions.py does not reimplement the serializer — it calls the REAL block_tree_serializer.block_to_action and renders the result in this same column set. So a diff here is a diff against production Python, not against a twin's approximation.
